# Agent Governance & Control Integration v1

How NEXUS keeps a model's proposed action behind the control plane, and what
that means for anyone operating it.

The authoritative contract is
[`contracts/AGENT_GOVERNANCE_CONTROL_CONTRACTS.md`](../contracts/AGENT_GOVERNANCE_CONTROL_CONTRACTS.md).
This document is the operational reading of it.

## The shape of the control loop

```text
model proposes an action
        ↓
control.Proposal built by the runtime   ← authority fields are not model-supplied
        ↓
governance.Engine.Evaluate             ← the one authoritative decision point
        ↓
ALLOW / ALLOW_WITH_CONSTRAINTS → the constrained effect happens
DENY            → blocked, structured `denied` observation, replan only
REQUIRE_APPROVAL→ blocked, approval record, execution pending
ESCALATE        → blocked, existing escalation → attention
```

One admission point per consequential effect. For tool calls it is
`agentexec.Runtime.Admit` on `InvokeToolScoped` — the single mediated tool path —
so the intelligence loop, delegated children and workflow steps are all admitted
before `Platform.Invoke`. That includes the in-process builtin fallback used when
no capability platform is configured: it is an execution path too, so it is
admitted rather than treated as an exception. Delegation and durable memory
writes/deletes are admitted in the loop immediately before the effect.
`model_call`, `memory_read` and the loop-control actions are not admitted: they
have no side effect beyond work the request was already admitted for.

`Platform.Invoke` is unreachable for a refused tool call, no child execution
starts for a refused delegation, and no record is written or deleted for a
refused memory action. No adapter knows governance exists.

## What the model may and may not say

The model supplies only `action`, `resource`, `resource_type`, `tool_id`,
`operation` and the invocation input. Everything that carries authority is
established by the runtime from the admitted request:

| field | established from |
|---|---|
| `actor_id` | the authenticated identity of the request |
| `business_id` / `division_id` | the request context (G3 already checked) |
| `agent_id` | the agent the runtime selected |
| `objective_id` / `execution_id` / `step_id` | the running objective |
| `correlation_id` | the request correlation |
| `proposal_id` | generated by the runtime |

`agentintel.Action` has no field for any of those, so this is structural rather
than a promise about model behaviour. A proposal that cannot name its own
authority is refused before governance is consulted.

## Governing an action

Write a normal policy through `/api/v1/control/policies` and pin it to the
action. `resource_type` uses the schema's own vocabulary (`tool`, `memory`,
`agent`, or `all`).

```jsonc
{
  "policy_type": "access_control",
  "action":   { "action_type": "custom", "action_ids": ["tool_call"] },
  "resource": { "resource_type": "tool", "resource_ids": ["http.request"] },
  "effect":   "REQUIRE_APPROVAL",
  "precedence": 1000,
  "approval_config": {
    "approver_type": "human",
    "approver_ids": ["nx:human:ops-1"],
    "timeout_seconds": 600,
    "auto_deny_on_timeout": true,
    "self_approval_prohibited": true
  }
}
```

Any of the five canonical effects works the same way: `DENY`,
`REQUIRE_APPROVAL`, `ALLOW_WITH_CONSTRAINTS`, `ESCALATE`, `ALLOW`. The engine's
own rules apply unchanged — more-restrictive-wins, scope precedence, default
`DENY` when nothing matches. Governance never becomes more permissive than the
policies you wrote.

The `action_ids` and `resource_ids` above gate tool calls. To gate a
delegation or a durable memory write, use its own action and resource type:

| what you want to gate | `action_ids` | `resource_type` | `resource_ids` |
|---|---|---|---|
| a capability | `["tool_call"]` | `tool` | the tool id, e.g. `http.request` |
| delegation | `["delegate"]` | `agent` | the child agent id |
| durable memory writes | `["memory_write"]` | `memory` | leave empty to cover every key |
| durable memory deletes | `["memory_delete"]` | `memory` | leave empty to cover every key |

Memory writes are admitted on their own merits rather than trusted because they
are in memory, so a record claiming authority is refused exactly like any other
action would be.

## Enforceable constraints

`ALLOW_WITH_CONSTRAINTS` returns restrictions that become runtime restrictions,
not commentary. The enforced set is closed:

| `constraint_type` | `expression` | effect |
|---|---|---|
| `tool_allowlist` | comma-separated tool ids | another tool fails closed |
| `operation_allowlist` | comma-separated operations | another operation fails closed |
| `max_duration_ms` | positive integer ms | tightens the call budget (never widens) |
| `resource_restriction` | comma-separated resource ids | another resource fails closed |

Rules worth knowing:

- `severity: mandatory` (the default) must be enforceable, otherwise the action
  **fails closed** — never silently ignored.
- `severity: advisory` is recorded in the observation and in
  `governance.constraint_applied`; by definition it is not a restriction.
- An unknown `constraint_type` fails closed.
- A model cannot remove, weaken or "ignore" a constraint: constraints travel from
  the decision into the request, and the capability platform still applies its
  own allowlist, scope and manifest gates afterwards.

## Approvals

```text
proposal → REQUIRE_APPROVAL → record → approver → APPROVED
         → RE-EVALUATE GOVERNANCE → ALLOW → capability
```

The record is bound to a fingerprint over the correlation, execution, objective,
actor, business, division, agent, action, resource, resource type, tool,
operation and the constraint set. Consequences:

- approving one action never approves another, even a nearly identical one;
- the approval authorizes exactly **one** admission after the resume — the same
  objective proposing the same action again needs a fresh approval;
- it never overrides an explicit `DENY`, a revoked identity, a suspended
  business or division, a disabled capability, a changed scope, or a security
  rejection, because re-evaluation is authoritative and the capability platform
  still gates afterwards;
- the requester cannot approve their own request, and an approver outside the
  policy's list is refused.

Approving is `POST /api/v1/approvals/{id}/approve?business_id=…` and returns 202:
the resume is an asynchronous re-run. Watch
`GET /api/v1/intelligence/{id}?business_id=…` for the outcome.

## Escalation

`ESCALATE` keeps the action blocked, publishes the existing `governance.escalated`
fact with `gate: "agent_action"`, and lets the existing intake queue the
escalation and file the attention item. The escalation carries the correlation
and objective context.

Attention prioritizes and interrupts. It never authorizes: acking or resolving an
alert changes nothing about whether an action may run, and any action that
follows must pass admission again.

## Governance is not execution

The loop distinguishes all of these, and none of them is collapsed into another:

| state | meaning |
|---|---|
| `denied` | governance refused; no side effect; the objective may replan within its remaining authority |
| `pending_approval` | stopped before the side effect, waiting for a human |
| `escalated` | blocked and handed to attention |
| `failed` | the work itself failed |
| `unknown` | a mutation's remote outcome could not be observed (Operational Reliability) |

`unknown` stays `unknown` and is never automatically re-dispatched, and it is
never mistaken for approval or for a governance outcome. The two axes —
governance state and execution outcome — remain separate all the way to the
response.

## Audit trail

| event | meaning |
|---|---|
| `governance.action_proposed` | a proposal exists (new) |
| `governance.decided` | the admission decision, with matched policy provenance (existing type, now published) |
| `governance.constraint_applied` | constraints became runtime restrictions (new) |
| `approval.requested` / `.approved` / `.denied` / `.expired` | the approval lifecycle (existing) |
| `governance.escalated` | escalation handed to attention (existing) |

Payloads carry ids, scope, action, resource, outcome, matched policy id and
version, and constraint ids. No prompts, no chain-of-thought, no tool output, no
credential material. Events are facts: no event grants authority, and no consumer
of an event may execute an action without admission.

## Durability (G4)

Approval and escalation records are **process-local**, exactly as before this
milestone. After a restart:

```text
old approval  → unavailable (404)
old execution → unavailable (404)
```

Nothing about that is durable and nothing pretends otherwise. Re-request
approval; re-submit the work. There is no durable approval workflow and no
durable execution recovery in this milestone.

## Scope

`MembershipSet.AllowsScope` remains the only scope authority, and admission never
establishes scope — it asks governance about an action inside a scope the request
pipeline already authorized. A foreign business or division is invisible (G5), and
suspended or archived scopes still admit no new work (G2). There is no RBAC, no
owner or superuser behaviour, and no model-controlled permission (G1).

## Deferred / out of scope (written down, not implemented)

Scheduler, event-triggered automation, browser automation, unrestricted shell,
arbitrary code/WASM execution, distributed execution, durable execution recovery,
persistent (durable) approval workflow, RBAC, multi-instance governance,
autonomous privilege escalation, a general-purpose policy DSL or expression
evaluator, tool self-installation or modification, vector DB / embeddings / RAG /
knowledge graph, UI, virtual office.
